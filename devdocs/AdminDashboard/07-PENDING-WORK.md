# Explicit remaining capabilities and acceptance gates

The working staff console is not a claim that all previously planned product epics or financial partners are complete.

| Scope | Actual current capability | Remaining requirement |
|---|---|---|
| Actual QPay execution | Configured adapter boundary and original-reference investigation | Contract, sandbox/live acceptance, complete funding/settlement mapping |
| Refunds and returns | Linked immutable investigation records, roles, evidence | Independently approved provider-supported compensating execution and ledger reconciliation |
| Treasury and suspense | Ledger accounts, liabilities/fees/holds, unmatched import and owner cases | Independently verified bank/provider balances, float alerts, complete three-way settlement and approved journal resolution |
| Pricing and catalogue | Immediate versioned policy approval, product purchase controls, adapter catalogue | Future-effective policy scheduling and configurable versioned provider mapping administration |
| Notifications | 175 reviewed metadata entries, intent/event inspection, safe suppression | Live Novu Framework/provider sync, delivery/bounce/complaint correlation, controlled template publish |
| Identity and evidence | Private upload storage interface, manual review, reasoned access | Real identity provider/liveness and production storage/scanner/data-retention acceptance |
| Reports and support | Bounded CSV, encrypted conversations, assignment/escalation | Asynchronous all-record exports, regulator-specific reports, live inbound email and service-level automation |
| Specialised products | Explicit unavailable boundary | Separately approved cards, savings, lending, business banking, growth economics and providers |
| Security and deployment | Origin/CSRF/MFA/roles, tests, non-root deploy template and runbooks | Independent security review, load/restore drills, operator assignment, final production acceptance |

Never resolve an integration gap by hiding an error, creating fake bank details, inventing a token, directly changing a balance, disabling a failing assertion, or using an in-memory review result as provider evidence. Each requirement must have source, tests, owner, operator acceptance and provider evidence where applicable before its feature row can be promoted.
